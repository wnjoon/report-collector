# 에이전트가 결제하면 책임은 누가 지나 — 팀 공유용 정리

- 출처·작성자: Bloom
- 발행일: 2026년 9월 28일
- 원문: https://blog.bloomworld.ai/who-is-liable-when-your-agent-pays/
- 성격: Ripple·t54·Tenity 공동 주최 「Agentic Payments Onchain」 발표·패널·법률 대담 후기
- 정리 기준: 사용자가 제공한 전체 본문. 기업 설명·시장 수치·전망은 행사 발언으로 구분한다.

## 1. 한 줄 요약

에이전트의 서비스 탐색·결제는 실제로 시연되고 있지만, 시장 확산에는 **유료 API 공급, 다양한 결제 수단, 권한 통제, 분쟁·보증 체계와 법제**가 함께 필요하다.

## 2. 핵심 메시지 3개

1. **초기 시장은 추론·연산·데이터 구매다.** 에이전트가 작업 중 필요한 자원을 소액·단건으로 사는 시장이 먼저 열리고, 쇼핑은 배송·반품·환불이라는 추가 문제가 있다.
2. **결제와 신뢰는 별도 사업 영역이다.** 송금 기능에 더해 에이전트 소유자·위임 범위·상대방을 검증하고 분쟁 증거와 보증을 제공해야 한다.
3. **에이전트 결제 성장과 블록체인의 우위는 별개다.** 카드도 에이전트 결제를 지원할 수 있다. 한국에서는 API 개방·제도·국제 표준 참여가 추가 과제다.

## 3. 배경과 문제의식

에이전트가 소비자가 되면 서비스 탐색부터 가격 확인·구매·결제까지 자동화할 수 있다. 그러나 사람 중심의 인증·결제·분쟁 절차에 새로운 참여자가 들어오므로, 기술 구현과 함께 권한·책임 구조를 다시 설계해야 한다. 원문은 이 문제를 기술, 시장 기회, 위험 통제, 한국 법제의 네 관점에서 살핀다.

## 4. 주요 내용 정리

### ① Ripple·Tenity: 기술 도구와 생태계

Ripple의 Joel Mun은 XRP Ledger가 송금·토큰 발행 기능을 코어에 제공해 API 연결로 활용할 수 있다고 설명했다. XRPL AI Starter Kit, t54의 오픈소스 x402 SDK, Stripe·Tempo의 MPP SDK 지원도 소개했다.

Tenity는 2023년부터 Ripple과 빌더를 지원하며 스타트업과 금융기관을 실증·파일럿·투자로 연결한다고 설명했다. 에이전트 결제는 기술 도구뿐 아니라 판매자·금융기관·투자자의 연결도 필요한 생태계라는 맥락이다.

### ② t54: 결제 처리보다 신뢰 계층

t54는 금융 시스템과 서비스 제공자 사이의 위험 관리 회사로 자신을 설명했다. 기관용 Trustline이 확인하는 것은 세 가지다.

- **신원:** 에이전트의 소유자와 실행 환경까지 확인한다.
- **위임:** 거래가 사용자 요청·예산·허용 범위에 들어오는지 판단한다.
- **증거·보증:** 분쟁 근거를 남기고, 승인·보증한 거래에 카드사와 비슷한 역할을 지향한다.

KYC는 고객 확인, KYT는 거래 위험 분석, KYA는 에이전트의 신원·권한 확인을 뜻한다. t54는 이들을 위험 엔진의 입력으로 쓰고 최종 승인·거절 및 분쟁 대응에 가치를 둔다고 설명했다. 구체적인 보상 범위와 조건은 본문에 제시되지 않았다.

### ③ 실제 데모: 유료 추론 서비스 자동 구매

Sergio Chan은 Codex에 자연어 지시를 넣어 리서치 에이전트를 만들었다. 흐름은 다음과 같다.

**XRPL AI Hub에서 서비스 탐색 → DeepSeek 선택 → x402 견적 확인 → 지출 권한 부여 → 답변 생성·메인넷 결제 → 거래·인보이스 확인**

0.01 RLUSD는 실제 가격이 아니라 지출 상한이다. 판매자의 동적 가격에 따라 실제 지출은 달라진다. 판매자 등록·심사, 거래 위험 심사 옵션, 지갑 없이 접근하는 신용 계정도 소개됐다.

데모는 디지털 서비스의 탐색과 결제가 연결되는 모습을 보여준다. 일반 쇼핑의 배송·환불까지 완성했다는 의미는 아니다.

### ④ 왜 블록체인인가: 결제 중립성과 프로그래밍 가능한 돈

| 발표자 관점 | 주요 주장 |
|---|---|
| 유준혁: 결제 중립성 | x402는 카드와 경쟁하기보다 다양한 결제 수단을 연결하는 방향 |
| 엄정용: 기계의 결제 도구 | 개인 키와 프로그램으로 결제를 실행하는 블록체인의 특성이 에이전트에 적합 |
| 이선민: 글로벌 사용 범위 | 플랫폼별 선불 충전금은 국경·서비스를 넘나드는 에이전트의 활동을 제한 |
| 규칙 기반 지출 | 시간·금액·횟수 조건을 결제 실행에 적용하는 도구가 중요 |

이들은 블록체인의 장점을 강조했지만 패널 전체가 블록체인 독점론에 동의한 것은 아니다. 블록체인 사용이 법적 인격이나 면책을 부여하지도 않는다. 중개자 위험을 줄인다는 주장과 모든 발행사·지갑·운영 위험이 사라진다는 주장은 구분해야 한다.

### ⑤ 쇼핑보다 API·추론·데이터 시장이 먼저

일반 쇼핑에는 잘못된 구매, 배송 사고, 반품·환불이 따른다. 반면 API는 작은 금액으로 빠르게 서비스를 제공하기 쉬워 초기 적용처로 제시됐다.

- **BlockRun AI:** 돈을 받고 여러 모델의 요청을 중개하는 사례.
- **추론·연산:** 에이전트가 작업할 때 반복적으로 소비하는 자원.
- **유료 데이터·API:** 계약 비용 때문에 열기 어려웠던 작은 거래를 단건 구매로 제공할 기회.
- **Cloudflare Pay Per Crawl:** 웹 접근을 차단하거나 무료 개방하는 것에 더해 유료 접근을 제시하는 사례.

엄정용은 같은 모델·무료 데이터만으로 결과를 차별화하기 어려워 유료 데이터 수요가 늘 것으로 봤다. 이는 전망이며 유료 데이터가 항상 더 좋은 결과를 보장하는 것은 아니다.

### ⑥ 한도·환불·평판: 여러 층에서 통제

원문은 위임·도구·계정 단계의 통제를 설명한다.

- AP2의 위임 단계에서 예산을 설정한다.
- 에이전트 도구·인프라에서 건별·일별 한도를 적용한다.
- 스마트 계정에서 금액·기간별 예산·결제 횟수를 제한한다.
- 프로토콜이 다루지 않는 환불·분쟁은 서비스와 인프라에서 보완한다.

프롬프트 인젝션은 외부 콘텐츠가 에이전트의 지시를 바꾸도록 유도하는 공격이다. 가짜 여행 판매자나 한도 초과 유도가 사례로 제시됐다. 상대방의 거래 이력과 평판도 중요하다는 주장이다.

판매자 보호도 필요하다. 유준혁은 결제 전에 작업하는 흐름에서 가짜 결제로 자원만 소모시키는 위험을 지적했다. 모든 x402 구현이 같은 순서를 따른다고 단정하기보다, 결제·제공 순서와 상대방 신뢰를 함께 검토해야 한다는 문제 제기로 읽어야 한다.

### ⑦ 한국의 병목: 도입·API 개방·국제 표준

이선민은 한국의 에이전트 활용과 외부 에이전트가 구매할 API 공급이 부족하다고 평가했다. 플랫폼 내부 자동화만으로는 개방된 에이전트 시장을 만들기 어렵다는 문제의식이다.

전자서명·공인인증서와 액티브X 경험을 들어 국내 독자 규격보다 국제 표준 논의에 참여해야 한다고 주장했다. 초기 인프라 구축은 도움이 됐지만 폐쇄적 규격은 글로벌 접근을 막았다는 교훈이다.

유준혁은 과거 21.co의 소액 결제 실험과 달리 지금은 낮은 수수료의 결제망과 에이전트라는 잠재 구매자가 있다고 봤다. 다만 에이전트도 카드를 쓸 수 있으므로 블록체인의 지속적 경쟁우위는 별도로 입증해야 한다고 강조했다. 다른 패널은 신규 시장 기회를 더 낙관적으로 봤다.

### ⑧ 법률 대담: 직접 사용과 타인 대상 사업의 구분

넥스트증권 조수한 준법감시인은 자동화 계약·결제도 사용자 행위로 귀속될 수 있으며, 자동화 자체가 일률적으로 금지되는 것은 아니라고 설명했다.

반면 투자 알고리즘을 타인에게 제공하면 실제 기능에 따라 투자자문·일임 등 규제 문제가 생길 수 있다고 지적했다. 소프트웨어라고 이름 붙인다고 규제를 피하는 것은 아니라는 취지다. 모든 봇 판매에 같은 인허가가 필요한지는 서비스 구조별로 검토해야 한다.

본문의 자기책임 설명과 최종 손해배상 책임도 구분해야 한다. 사용자·판매자·금융회사·개발사·보증 제공자의 책임은 계약, 적용 법률, 권한·오류·기망의 구체적 사정에 따라 검토한다. AI가 실수하면 무조건 사용자가 전액 부담한다는 결론으로 확대해서는 안 된다.

### ⑨ 스테이블코인과 에이전트 결제는 별개 의제

조수한은 국내 스테이블코인 제도와 사업 기반이 부족하다고 평가했다. 규제 대응 부담, 수익 모델 부족, 제도 정비를 기다리는 동안의 투자 여력도 문제로 제시했다.

그러나 에이전트 결제 전체가 불가능하다는 뜻은 아니다. 원문은 실험과 사업화는 가능하지만 착오·피해 구제 체계가 충분하지 않다고 설명한다. 이는 행사 시점의 평가이며 개별 사업의 적법성 판단과 구분해야 한다.

증권사의 관심은 새 결제 프로토콜 연구보다 자산 토큰화와 기존 투자 서비스 연결에 가깝다는 설명도 나온다. 넥스트증권은 API 트레이딩을 원하는 고객을 위한 플랫폼을 목표로 소개했다.

마지막 실무 조언은 **감당 가능한 손실 한도를 먼저 정하고 이를 프로토콜·알고리즘으로 강제하라**는 것이었다. 기술·신뢰·법률의 답이 한곳에서 완결되지 않았다는 점이 글의 결론이다.

## 6. 공유용 요약

### 짧은 버전

에이전트가 유료 API를 찾아 실제 결제하는 흐름은 이미 시연되고 있다. 초기 기회는 추론·연산·데이터의 소액 거래이며, 쇼핑 확산에는 환불과 분쟁 해결이 더 필요하다. 결제망뿐 아니라 신원·권한·증거·보증을 제공하는 신뢰 인프라가 중요하다. 한국에서는 API 개방, 제도 정비, 국제 표준 참여가 추가 과제로 제시됐다.

### 조금 긴 버전

Bloom 행사 후기는 에이전트 결제를 기술·사업·위험·법률 관점에서 다룬다. Ripple과 t54는 실제 유료 추론 구매와 메인넷 결제를 시연했다. t54는 결제 처리보다 에이전트 신원, 위임 범위, 분쟁 증거와 보증에 사업 가치를 둔다. 초기 시장으로는 쇼핑보다 API·추론·데이터 거래가 제시됐다. 단건 유료 접근은 기존에 계약 비용 때문에 열기 어려웠던 작은 시장을 만들 수 있다. 블록체인은 글로벌 접근성과 규칙 기반 결제에 장점이 있지만 카드 대비 경쟁우위는 확정되지 않았다. 한국은 에이전트 도입, 외부 API 개방, 국제 표준 참여와 제도 기반이 병목으로 지적됐다. 법률 대담은 직접 자동화와 타인 대상 금융 서비스 제공을 구분해야 한다고 설명했다. 팀의 도입 판단에서는 감당 가능한 손실 한도와 사고 처리 주체를 먼저 정할 필요가 있다.

## 7. 팀 시사점 — 추론

- **제품·개발:** 소액 디지털 서비스부터 검증하고 예산·판매자·작업 범위를 모델 밖에서 강제한다.
- **사업:** 에이전트가 구매할 데이터·API와 신뢰·보증·분쟁 서비스를 각각 기회로 평가한다.
- **운영·금융:** 거래량뿐 아니라 오결제·미제공·환불 비용까지 포함해 경제성을 본다.
- **법무·정책:** 위임 기록과 책임 약정을 준비하고 금융 기능·자산 취급 방식별 규제를 검토한다.
- **투자:** 결제량 증가를 특정 토큰이나 체인의 가치 상승과 바로 연결하지 않는다.

## 8. 더 생각해볼 질문

1. 에이전트가 반복 구매할 만큼 가치 있는 우리 데이터·API는 무엇인가?
2. 건별·일별·작업별로 얼마까지 자동 결제를 허용할 것인가?
3. 결제했지만 서비스를 받지 못하면 누가 환불·보상하는가?
4. 사용자 위임과 실제 거래를 연결해 입증할 수 있는가?
5. 수익성이 검증되기 전에 제도 정비를 기다려야 하는 사업은 아닌가?
